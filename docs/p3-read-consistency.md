# P3 读取快照一致性与双会话恢复（本机）

## 读取期间发生业务变化

此前 epoch/history guard 保护会话重置和历史保留水位，但资产、metadata、配额、onboarding 和用户信息分别读取，业务更新可能让请求混合多个状态。新增 0019_sync_read_guards：在最终投递登记的同一 D1 batch 中，检查本次认证读取的资产单调版本、onboarding 版本及 user.update_id，才允许登记事件和 Complete。

资产/metadata 或 AuthUsersV2 请求检查 owner 的资产版本；UserMetadataV1 检查 onboarding；UserV1/AuthUserV2 检查用户版本。按请求家族启用，其他账号的写入及未请求家族不阻塞。新守卫与原有 epoch、history guard 并存，不改变旧 sync_guards 六列结构或 ACK 格式。

检查失败返回 409，不注册旧快照的 Complete、不提交显式 reset 的检查点清除与 epoch 变更，原检查点保留。重试重新鉴权和收集，完成后才允许 ACK。请求登记提交后的业务变化属于下一轮，不能据此删除已提交的有效投递。持续写入可能造成读取重试，尚未做重负载/平台预算验收；CPU 超预算继续暂缓。

认证仍使用相同会话和 bcrypt 安全配置。新增版本在同一认证 SELECT 中读取，不将额度或用户变化当作已经被旧 payload 确认。migration 0019 只增加临时守卫，不重写既有资产、原图、预约或检查点。

## 独立双会话关系模型

本机新增 SQLite 消费模型，启用 owner、metadata 外键与事务。按事件类型应用用户、资产、收藏、metadata、删除、onboarding；重置时清空已支持家族，失败则事务回滚。它是独立的简化消费者，不是官方 App、官方完整数据库或真机替代。

两会话执行 32 轮有界工作负载：JPEG/PNG 上传与重复、收藏/metadata 更新、4 次资产退役、onboarding 更新/删除、一端长时间离线、一端正常同步。覆盖客户端应用中断不 ACK、未送达 ACK 的事件重放、ACK 已提交但响应丢失重试、两次显式 reset，以及日志压缩后离线端收到 SyncResetV1 再重建。最终按资产 ID、owner、收藏、名称、尺寸、metadata 和 onboarding 与服务端逐项对账，两端一致；退役原图和预约仍保留。

该测试没有抬高每账号 20 个逻辑项配额、4 MiB 或像素限制。现有 10,000 合成删除元数据测试继续保留，但不冒充 1,000 真实资产验收。

## D1 引用检查

内部 storageInventory 新增 references 模式，按 D1 引用分页，再对本页最多 20 条引用执行 HEAD，包含没有 R2 对象的 integrity_copy_intents。全部六类引用在一次只读 D1 batch 中分别有界查询，每类最多 21 条，合并排序取 21 条判断下一页（最多读取 126 行候选）；避免六路 UNION 触发 D1 compound-SELECT 限制。

缺失、不可用、大小/摘要不匹配分别报告；摘要/上传预约仅标记 present-unverified，不冒充已发布或原生摘要验证。缺失/老旧/损坏预约一律保留。查询失败整页 503，HEAD 失败逐项 unavailable，均不清理引用或字节。跨账号引用键不对外回显。此为本机内部观察，生产维护路由未接入。

## 运行

使用 pnpm db:migrate:local 后运行 pnpm dev:local，需要本机 0019；收藏原型还需 0020。不要使用默认 pnpm dev 连接尚未迁移的远程数据库。用户随后明确要求开发后部署 dev 并在 dev 调试；完整回归通过后前向迁移并发布，再单独记录公网结果。检查通过前不要混用远程0018与本机新代码。
