# P2 curl 复测：4 MiB 上传与探针超时

日期：2026-10-16。分支 dev，本机开发。只调整探针、测试与文档，没有修改或部署 Worker；官方 App、bcrypt、reset/ACK 均不变，CPU 超预算优化继续暂缓。

本机条件：Windows、Node.js 24.9.0、pnpm 11.25.0、curl 8.21.0/Schannel，上传使用 HTTP/1.1。新增报告 proxyUsed=0；没有采集网络类型，也未改变系统代理或 TLS 验证。

## 首轮结果与定位

使用仓库原有 `node scripts/mixed-queue-probe.mjs --curl`，10 项上传检查均完成：普通图片去重 200，超限 413，HEIC/视频/Live Photo/sidecar 等拒绝 400；随后剩余步骤超时，原脚本未记录准确阶段，不能将此轮写成完整闭环通过。

| 超限     |  4194305 |        4194721 |                 27.477 |       34.492 |  413 |

[首轮上传报告](contracts/p2-curl-first-upload.json)。请求体包含 multipart 边界与字段，与文件上限分开计算。

因此至少一部分此前的 30 秒失败可由本机传输等待不足解释：两个合法边界请求发送完成本身就超过 30 秒。本轮 curl 接近 4 MiB 上传并非稳定无法成功。该结果不能解释此前 HTTPS 连接重置或 120 秒等待失败的全部原因，不能把不同 TLS/HTTP 客户端、不同时间的样本当成严格受控性能比较。

## 探针修复

- 增加 DNS、TCP、TLS、传输准备、libcurl 发送完成、首字节、接收字节、代理使用与总时间白名单指标；不保存 IP、代理地址、请求头、凭据、原始 curl JSON 或响应正文。
- 每项上传和原图步骤持续写入进度，标明失败阶段、完成状态与会话退出结果；清理退出失败不覆盖原始失败。
- `--curl` 模式的原图读取也走 curl GET，逐字节比较，响应有 8 MiB 有界限制。登录、Sync/ACK 和退出继续沿用原有 fetch。普通模式保持 fetch。成功后进度报告明确 complete=true，不再一直显示 false。
- POST 保持原有 120 秒诊断等待，curl GET 同样有界；这不是官方 App 超时设置，也不代表产品响应时间验收放宽。没有自动无限重试。

指标含义依据 [curl 官方手册](https://curl.se/docs/manpage.html)：time_posttransfer 是 libcurl 发送最后字节的时间，不证明服务端保存；time_starttransfer 是首字节，可能包含 100 Continue，不能直接视为最终响应或服务器 CPU 时间。proxyUsed=0 也不能排除系统透明代理/VPN。

## 回归

本地 HTTP 服务覆盖 4 MiB 实际字节、100 Continue、正文发送前的 413、完整原图 GET、上传完成后仍等待响应的超时、截断响应、响应大小上限、凭据配置注入拒绝及脱敏。确认提前 413 的 uploadedBytes 可为 0，响应超时也可能 uploadedBytes 等于完整请求体，不能混为同一失败阶段。

P2/G1 的官方 iOS 混合队列、失败项重试、真实图库及 Free 资源关口继续保留；HTTP 探针不等于官方 App 真机验证。

## 第二轮：已明确发送阶段失败

[第二轮完整进度](contracts/p2-curl-second-progress.json) 在 upload:below-limit 停止：请求体 4194720 字节，libcurl 只上传 1818624 字节，12.740 秒出现 CURL_55，发送完成时间为 0，仅收到 100 Continue，没有最终响应；退出会话为 200。按 curl 手册，55 是发送网络数据失败。因此该次请求不是“请求体已发送完、等待业务处理”的超时，也不是服务器最终返回了 HTTP 100 成功。

这将本次故障范围缩小到请求体尚未完整发出的连接路径，但不足以定位本机、透明代理、网络或 Cloudflare 的具体责任，更不能把所有历史失败都归于一个原因。未关闭 TLS 验证、未修改系统代理，未调整 Worker 安全或同步代码。

## 第三轮：重试恢复与间歇中断

[第三轮进度](contracts/p2-curl-third-progress.json)：上限减 1 字节重试成功，发送完成 28.665 秒、总计 33.818 秒、200；恰好上限在发送 1900544/4194718 字节后于约 24 秒报 CURL_55，仅收到 100，退出会话 200。原图读取和 Sync/ACK 尚未进入，该轮 complete=false。未自动无限重试，也未把临时 100 当成成功。

三轮结果证明接近 4 MiB 既有成功，也有发送中断；当前网络路径的完整队列仍不稳定，不能宣称所有超时已修复。没有扩大服务端文件限制或为了通过探针改变官方客户端。

## 原图独立读取：响应头成功不等于正文完整

以备份预检查确认既有的边界图片存在后，独立执行 curl GET，不重复上传：[原图报告](contracts/p2-curl-existing-media.json)。上限减 1 字节原图在约 1.420 秒收到首字节/200，但 120.015 秒只收到 3813056/4194303 字节，CURL_28；没有通过原图字节比对，后续第二张原图和 Sync/ACK 没有执行，退出 200。

这定位到另一个可区分的失败阶段：响应正文未完整传输。不能仅凭 HTTP 200 或快速首字节写成原图成功，也不能以请求体已发送完认定图片已持久化。本地新增 200 后正文停滞回归，要求保留 200、超时错误和部分接收字节，同时不判为完整成功。

本轮没有再次完成公网全队列原图/Sync/ACK，不能替代既往验收或新增真机结论。发送中断与响应体超时的具体网络/边缘根因仍未确定。CPU 超预算依用户要求暂缓，没有以降低安全校验来补偿网络延迟。

## 本地验证

最终复验曾再次暴露旧 upload-cancel 夹具间歇性 500。原因是注入合成流前真实 HTTP 请求体未消费，取消可影响 workerd 代理。测试入口补上真实请求体读取后再注入，并把上传读取失败/取消失败各连续执行五次，继续验证无资产、无意图/对象及后续恢复。这与公网 curl 的发送/接收失败是不同路径；没有合并云端环境配置或改变生产入口。

最终 `pnpm check` 的格式、lint、类型、70 项测试与 dry-run 构建全部通过，无失败或跳过；冻结契约校验 279 个操作/53 个来源通过。本轮没有部署权限或数据库配置变更。
