# P1 Sync reset / ACK 并发隔离

日期：2026-10-14。仅 dev，有界小图片实验；官方 App 保持不修改，冻结 Immich v3.3.1 / iOS 3.3.1 build 23。

## 缺陷与修复

原实现先读投递记录再写 ACK，两步之间 reset/清除检查点可能发生，旧请求随后重新写回检查点。已计算的旧流也可能在 reset 后登记投递。固定 `SyncResetV1|reset` 无法区分两次重置，重置确认响应丢失后重试可能清除新建检查点。

0007 为 sessions 增加 `sync_epoch`、`reset_ack`、`last_reset_ack`。流登记、普通 ACK、reset 开始/确认、清除检查点均通过 `sync_guards` 触发器校验，再在**同一个 D1 batch 事务**内执行写入和删除 guard。事务确认会话仍有效、轮次未变化；普通 ACK 整批检查投递归属、有效期与轮次后才写入。guard 不跨请求持久化；异常整批回滚。

依据：[Cloudflare D1 batch 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) 的批内顺序执行与失败整体回滚保证，2026-10-14 核实。会话期限与投递期限在事务时刻检查，不只依赖请求开始时的鉴权结果。

| 操作               | 原子行为 / 恢复                                                                               |
| ------------------ | --------------------------------------------------------------------------------------------- |
| 开始 reset         | 生成独立 UUID 轮次，保存本次 reset ACK，失效旧投递；保留检查点直到客户端完成 reset            |
| pending reset 的流 | 反复返回同一本轮 ACK；状态已变化则 409                                                        |
| reset ACK          | 仅接受本轮单独提交；首次清空检查点和投递、退出 pending；同轮重复确认 204 且不再清空           |
| 普通 ACK           | pending 时 409；旧轮次/未投递/过期 ACK 为 400 且字段定位 acks；整批原子拒绝                   |
| clear 全部/部分    | 删除指定检查点，保留其它检查点；更换轮次并失效所有旧投递；pending 时拒绝；空 types 不改变状态 |
| 已暂停的旧请求     | 事务开始时轮次不同、会话失效或状态不符则 409，不写入新状态                                    |
| 数据库结果不明确   | 503，重发原 ACK；已提交 reset ACK 的重试不会破坏重建结果                                      |

投递未确认有效期 24 小时；重新发出相同事件会刷新投递时间。已确认且属于当前轮次的检查点允许重复 ACK。游标仍单调推进，用户/资产顺序不变。

## ACK 与官方契约的边界

一般事件在发生 reset/clear 后使用 `type|原游标|轮次UUID`；reset 使用 `SyncResetV1|reset|轮次UUID`。Complete 的第二段仍是 UUIDv7，继续用于 30 天过期判断。轮次标识用于服务端隔离，不包含用户秘密。

这是相对于上游具体 ACK 编码的有意差异，不宣称服务端字节级一致。冻结源码 `mobile/lib/domain/services/sync_stream.service.dart` 中 `_processBatch` 先应用事件，再将 `batch.last.ack` 原样交给仓库；reset 后重新请求流。因此客户端无需解析新后缀或修改代码。源码证据见既有 [来源索引](contracts/p1-small-images-sources.json) 和 [Sync 调查](sync-contract.md)；本轮不更新冻结版本。

升级保留原会话和检查点：初始轮次为空时继续使用已存在的 ACK 格式，首次 reset/clear 才切换到隔离轮次。迁移时已 pending 的旧 reset 保留一次 `SyncResetV1|reset` 确认路径。部分 clear 保留的其它检查点仅作进度，不能用旧轮次 ACK 继续确认。

服务端保证事务顺序和检查点隔离，不能撤回已经发往网络的旧响应。客户端需按原有流程先应用/确认 reset 再拉新流；多条网络响应延迟、手机进程崩溃等实际消费行为仍需真机验证。显式再次发送 `reset:true`（前一次 reset 已确认之后）会启动新轮次；该请求本身没有幂等键，不承诺与重发原 reset ACK 等价。
