# P2 备份预检查与原图恢复

2026-10-16，对应 P2-01 去重、P2-02 跨存储恢复、P2-04 重试。

## 问题与行为

原先 bulk-upload-check 只看 D1 元数据。原图丢失时仍返回 duplicate，依赖预检查的客户端可能跳过重传，无法触发已有上传恢复路径。

现在仅检查当前用户、请求中命中的资产：R2 HEAD 确认存在且大小与 D1 一致才返回 duplicate。确认缺失或大小不符则返回 accept，允许客户端重传；上传端恢复同一对象键并返回已有资产 ID，不新增资产、预约或同步版本。重传仍先执行文件大小、格式、Live Photo 与内容校验和检查，不绕过安全防护。

同一请求内重复校验和只查询一次 R2；未命中和空列表不查询 R2。当前每账户最多 20 项，因此最多 20 次 HEAD。HEAD 异常返回 503、assets 字段及重试要求，不能作为原图丢失或已备份的证据。没有新增数据库迁移。

返回结构沿用仓库冻结的 Immich v3.3.1 OpenAPI AssetBulkUploadCheckResponseDto，官方 App 不修改。这里只保证该接口的服务端语义，不声称所有 iOS 备份路径都会调用它，也不声称客户端自动恢复已通过真机验证。

## 验证范围

本地 Worker/D1/R2 回归：正常重复、未知/跨用户校验和、空列表、重复查询合并、HEAD 失败；实际删除或替换测试账户的 R2 对象后允许重传，两次并发重传恢复字节，D1 行及同步版本完全不变、无新增预约和孤儿对象，Sync/ACK 正常。故障注入只在测试入口，生产入口不识别测试控制头。

公网脚本 `node scripts/bulk-recovery-probe.mjs` 使用已存在合成图片，验证预检查重复/接受、原图和 Sync/ACK。不会删除或破坏 dev 原图，因此线上缺失/损坏恢复没有直接注入验证。

## 局限与剩余任务

HEAD 只能判断存在和长度，不能识别等长内容损坏；检查之后对象状态仍可能改变。此机制不是存储完整性审计，也不修复损坏的 D1 元数据。重传恢复能力仍受当前支持格式及 Live Photo 防护限制。

额外 R2 HEAD 带来请求成本和延迟；未完成新 CPU/额度实测，CPU 超预算依用户要求继续暂缓。密码安全性与 reset/ACK 并发隔离不降低，test/生产不发布。P2/G1 仍待真机混合队列、失败重试、真实图库和资源验收，不据此宣称完整备份。
