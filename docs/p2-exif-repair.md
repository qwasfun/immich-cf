日期：2026-10-15。CPU 超预算继续暂缓，官方 App、bcrypt cost 12、reset/ACK guard 不变。

## 同步版本与提交边界

迁移 0009 增加资产 `sync_seq`，已有记录初值等于原 `seq`，因此旧检查点仍有效。单行时钟从现有最大序号初始化；新插入及实际宽高变化通过 SQLite 触发器分配更高版本，和业务修改同事务提交/回滚。Sync 按 `sync_seq` 排序并编码原格式 ACK，不改变资产 ID、原始插入序号或客户端协议。

读到旧快照的请求即便晚到并被 ACK，也只能确认旧版本；之后的增量会再次发送同 ID 的新尺寸，客户端沿用既有 upsert。多个会话分别确认，不清空客户端检查点。资产元数据家族可能随资产版本重发，由原有 upsert 处理。当前实现合并中间尺寸状态，不是每一次变化的历史日志；没有新增删除语义。

## 修复入口

`POST /api/immich-cf/repair-dimensions` 为服务端维护接口，官方 App 不需要调用。请求 `{ "id": "资产 UUID", "apply": false }` 默认仅预检；显式 apply=true 才应用。仅允许当前有效会话所属用户的图片，不接受目标用户参数，不开放管理员越权。

逐资产校验 R2 原图大小、SHA-1 与记录一致，再使用既有受限 EXIF 解析确定尺寸；缺图、原图不一致和损坏 EXIF均拒绝。原图不改、不覆盖、不删除。更新语句比较旧版本/宽高/对象键/校验和并重新校验会话及禁用状态，冲突返回 409，请重新预检。单条更新与触发器原子推进版本；响应丢失后重试看到尺寸已正确，不再产生新版本。

`node scripts/repair-dimensions.mjs` 仅预检本机配置的 dev 测试账户；增加 `--apply` 才修复该账户当前最多 20 张图片。脚本使用临时会话，先确认旧快照，再修复并检查新增量、重试幂等，最后退出。每资产独立提交；中途失败可以重跑，不宣称整个图库是一个事务。其他账户需要以自己的身份独立执行。

迁移后尤其在修复发生后，不应回滚到只按 `seq` 同步的旧 Worker，否则旧版可能遗漏修复更新。保留 0009 数据结构，回滚也必须使用识别 `sync_seq` 的版本。修复不主动写回错误尺寸。
