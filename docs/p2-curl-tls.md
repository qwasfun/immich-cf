# curl 连接恢复、代理与 TLS 对照

日期：2026-10-16，dev 分支、本机开发。承接 [上轮 curl 诊断](p2-curl-retest.md) 的发送中断和 200 后正文未完整传输。本轮仅调整探针、回归与文档，不修改或部署 Worker。

## 本机入口

```sh
node scripts/mixed-queue-probe.mjs --curl --tls12 --recover --proxy http://127.0.0.1:7890
```

用户已确认仍使用上述本机代理。参数均为显式选择：不加 --proxy 不改变原有 curl 路由；不加 --tls12 保持默认 TLS 协商；不加 --recover 保持单次上传/完整 GET 的诊断行为。代理仅允许不含账户、密码和查询参数的 loopback HTTP 地址，不修改系统代理或路由。

登录、Sync/ACK 和退出仍使用原来的 fetch。tlsPolicy、proxyRequested 与 proxyUsed 描述 curl 的数据请求，不代表整个官方 App 或所有控制请求使用同一 TLS/代理路径。代理收到 CONNECT 也不证明其出站节点或规则一定走远端代理。

## 定位结果

- 以前报告 proxyUsed=0；系统代理开关关闭，但用户仍在使用本机代理，因此不能把系统开关等同于代理服务不存在。
- 显式连接 7890 时，TCP/CONNECT 成功（CONNECT 200），默认 TLS 的公开 healthz 在约 5 秒失败；加 TLS1.2-only 后约 1.75 秒收到 200，证书验证保留。
- 不经过显式代理、仅 TLS1.2-only 的单张原图对照曾在 20.643 秒成功。但同策略完整队列后来仍在 original-bytes 遇到 CURL_28。**强制 TLS1.2 单独不足以解决问题。**

见 [单样本](contracts/p2-curl-tls12-single.json)、[TLS1.2完整队列失败进度](contracts/p2-curl-tls12-progress.json)。默认协商的实际 TLS 版本并未被旧报告记录，不能据此断言 TLS1.3 或某个 Schannel 缺陷就是根因。

## 有界恢复

### 发送中断

恢复仅允许 /api/assets，要求显式内容校验和，复制固定请求体和请求头，最多三次尝试，共用 120 秒预算。只重试限定传输错误（18/28/52/55/56、未发送正文的 35）或 502/503/504；400/401/409/413 等拒绝不重试。所有尝试都保留在进度报告中，不把多次尝试隐藏成一次成功。重试次数与共享预算同时生效，证书验证错误不触发降级策略。

服务端原有 owner/checksum 去重和上传意图保持不变。即使已经提交、响应丢失，重传仍是同一图片，不改 ID/配额/同步版本。客户端重试本身不能代替服务端幂等保证；回归同时验证响应截断后的重复返回与逻辑资产唯一。

### 200 后正文超时

恢复模式不用整图 GET，而按最多 512 KiB 的 Range 读取：首个成功段取得强 ETag，后续发送 If-Range；逐段校验 206、Content-Range、总长、强 ETag 和实际段长。某段传输失败只重试该段，最多三次；单段等待最多 20 秒，单图总预算 180 秒，不无限重试。

弱或变化的 ETag、错误范围、服务器忽略 Range 返回 200、以及完整组装后与已知原图不一致，均失败且不交付组装内容。完成后仍逐字节比较整图，再执行 Sync/ACK。真实分段状态是 206，不伪报为服务器完整 GET 的 200。

分段会增加 HTTP、鉴权、D1 和 R2 调用；此为诊断/恢复功能，不宣称降低 CPU 或通过 Free 预算。180 秒恢复预算也不能当成产品性能验收放宽，不能直接与原 120 秒单 GET 作等预算性能比较。

## TLS 与安全回归

curl 的 --tlsv1.2 只约束最低版本，因此同时设置 --tls-max 1.2，依据 [curl 官方手册](https://curl.se/docs/manpage.html)。证书验证始终开启；不使用 insecure、不忽略吊销检查、不修改系统 TLS、Cloudflare 设置或密码参数。报告记录 certificateVerifyResult，原始请求头、证书详情和代理地址不写入报告。

纯本地 HTTPS 回归确认：不可信自签证书仍拒绝；仅 TLS1.3 的服务在 TLS1.2-only 下握手失败，均不能进入 HTTP 处理。证书/密钥是公开测试素材，不导入信任库、不对应真实服务，运行测试不需要安装 OpenSSL。

另外覆盖：显式代理实际承载请求、代理凭据/配置注入拒绝；上传响应中断后的幂等恢复；拒绝不重试、503 最多三次；部分范围响应断开后的同段恢复；弱/变化 ETag、错误范围、忽略 Range、等长错误内容拒绝。已有 4 MiB、100 Continue、413、正文停滞与 reset/ACK 回归继续执行。

## 验收边界

本轮不使用云端环境。CPU 超预算继续暂缓，官方 App、密码安全性和 reset/ACK 并发隔离不降低。这里实现的是本机 curl 探针的路由与恢复；不修改官方 App，也不声称其已经采用此恢复策略。curl 通过不能替代官方 iOS 混合备份、失败重试和真机验收，P2/G1 仍按原关口评估。

## 完整公网结果

上述显式代理 + TLS1.2 + 恢复命令完成本轮全闭环：[最终结果](contracts/p2-curl-recovery-probe.json)、[完整进度](contracts/p2-curl-recovery-progress.json)。10 项上传检查通过，共 10 次上传尝试；正常 PNG/JPEG、上限减 1、恰好上限均去重返回 200，超限 413，目标范围外格式/Live Photo 仍明确拒绝。

四张正常图片原图全部组装后逐字节一致。共有 22 次分段读取尝试，其中保留 4 次 CURL_35 连接失败，其对应分段重试后成功，不重新下载已验证的其他段。此轮没有再次发生公网 CURL_55；发送途中断开后的完整重传由本地真实 HTTP 接收中断测试验证，不虚构公网复现。

Sync 返回全部成功资产、ACK 204、随后增量仅 Complete、退出 200；进度为 complete=true、failure=null。curl 数据请求记录 proxyUsed=1，报告不保存代理地址、账户、令牌、原始头部或正文。proxyUsed 证明 curl 使用了指定代理，不能确定该代理的出站规则。

这给出了本机 curl 可用的有界恢复路径，**没有证明网络/代理/TLS 底层缺陷已消失**。四次失败仍在报告中；后续网络或代理节点变化需要复测。该次通过也不等于官方 App 已适配恢复逻辑或 Free CPU 关口已通过。
