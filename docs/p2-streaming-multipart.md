# P2 增量 multipart 解析与失败恢复

2026-10-17，对应 P2-01 流式 multipart、字段/长度约束与 P2-04 未知长度、中断和重试。

## 实现范围

上传入口逐块读取 Request.body 并送入 MultipartParser，不再先拼接整个原始请求体后调用 Response.formData。采用固定版本 @remix-run/multipart-parser 1.0.0；传递依赖 @remix-run/headers 1.0.0 由 pnpm-lock.yaml 锁定，均为 MIT。API 依据[上游解析器文档](https://github.com/remix-run/remix/tree/main/packages/multipart-parser)，实际验证对象为安装的固定版本，未跟随主分支自动升级。

请求总量仍最多 4 MiB + 64 KiB，单图片仍最多 4 MiB。支持带引号 boundary、大小写不同的 media type 和 UTF-8 文件名/字段内容；boundary 最多 70 个 RFC 合法 ASCII 字符，末尾不能有空格。每个分段头合计最多 8 KiB，解析期间超过上限即停止消费并取消读取；错误定位“上传分段头”，提示减少内容。传输中断仍返回 assetData 的恢复网络/重传提示；取消异常不覆盖原始错误，成功/失败都释放 reader 锁。

文本字段若无法解码为 UTF-8，错误定位到具体字段（例如 fileCreatedAt），提示重新生成有效 UTF-8 文本；字段名先检查字节长度与控制字符，错误不回显提交值。

文件分段仍保留有界缓冲，用于完整格式、XMP/EXIF、SHA-1 校验及 R2 写入；这不是无限大小上传、零拷贝或未经验证的 R2 直传。增量解析消除了旧的整请求拼接步骤，但未测量峰值内存或 CPU 改善，不据此宣称符合 Free 预算。

只有消费到 EOF 并通过 parser.finish 后才交给原上传流程。解析器可能在闭合分隔符后缀尚未验证时产出最后一个分段，因此不能在收到 File 时就创建预约、写 R2 或发布 D1 资产。非法尾部、截断、无效 UTF-8 和重复文件均不得留下成功资产。存储流程继续沿用预约、原生 R2 SHA-1 确认、D1 事务及同图去重。

## 保留防护顺序

完整表单仍先检查字段名与重复字段，再执行 Live Photo 持久登记，然后执行 32 字段、单项 8 KiB/合计 16 KiB UTF-8 文本、文件类型和图片大小约束。解析器单分段上限使用请求上限，而不是提前使用 4 MiB 文件上限，避免请求总量合规的超大动态分段在读取后续设备标识前被拒绝，丢失原本可登记的 Live Photo 负面证据。另设 1024 分段的解析防护上限，业务上限仍为 32；不是允许上传 1024 个有效字段。

格式不完整、分段头/解析分段数超限或超过整个请求上限时无法保证后续设备字段存在，与此前整体解析失败一样，不据此推断未标记文件是独立静态图。既有 Live Photo 标识缺失/未到达等限制仍有效。不修改官方 App、密码 KDF 或 reset/ACK 代际与事务隔离。

## 回归矩阵

- 实际本地 Worker 中在 HTTP 请求接收后注入单字节、17 字节分块，保证边界及多字节中文跨块；验证文件名、mobile-app 元数据、原图字节、原生 R2 校验、同图去重及 Sync/ACK。
- 分段头恰好 8 KiB 成功；超限头提前取消，reader 解锁。测试夹具先接收真实 HTTP 正文再合成分块，因此只证明应用消费提前停止，不声称真实 TCP 上传一定提前停止。
- 最后分段已经产出但闭合后缀非法、尾部 CRLF 损坏、关闭分隔符截断、重复文件、无效 UTF-8：400 和预期字段，资产/预约/R2 无残留，随后正常图片 201/200 恢复。
- 4 MiB 加 1 的动态分段在请求总量范围内仍先登记标识、再返回 413；对应静态重试继续拒绝。已有流读取/取消失败、未知长度、大文件、混合队列、原图异常、密码和 reset/ACK 回归继续执行。

## 验收与剩余项

公网脚本 `node scripts/multipart-probe.mjs` 复用本机代理 http://127.0.0.1:7890、curl TLS 1.2、单次最多 60 秒/总计 120 秒/最多三次上传尝试，以及强 ETag 分段重试。验证 7 种非法请求、精确头边界与同图重传、原图/预检查/Sync/ACK；公网没有注入合成分块或存储故障。另运行完整混合探针覆盖 4 MiB 边界。小 JSON 网络失败最多整轮复验一次；每次失败保留报告，不无限复跑或把环境波动判断成服务端缺陷。
